# piano 启动记录 — 构建 `43001198573`（`28ab843`）

真机实测，2026-11-11 20:25（北京时间），设备 `25091RP04C`（piano，SM8750，slot `_b`）。
这一版包含三分钟 payload 窗口（`28ab843`）、`PublishVolume` 直接引用 stage 传输缓冲
（`c75b22e`）以及 payload 卷独立的设备路径 GUID `3E7B9C41-8D52-4A6F-B1C7-2A5E9D4308BF`
（`eb57fc5`）。

## 1. 主机侧：payload 发布成功

```
$ fastboot boot boot-43001198573.img
Sending 'boot.img' (3088 KB)                       OKAY [  0.074s]
Booting                                            OKAY [  0.225s]

$ # 9 秒后 UEFI 重新枚举上来（getvar product = piano-uefi）
$ fastboot stage payload-43001198573.img
Sending '...payload-43001198573.img' (163840 KB)   OKAY [  3.918s]

$ fastboot oem ramdisk
OKAY [  0.011s]
```

`oem ramdisk` 从上一版的 `FAILED (remote: 'cannot publish the payload')` 变成
`OKAY [0.011s]`，且 UniXNU 菜单随即给出了 `xnu` 条目（机主确认可以引导）。

结论（真机读出，不是推断）：`InstallMultipleProtocolInterfaces` 之前在
`A9C6827C-…` 设备路径上返回 `EFI_ALREADY_STARTED`，换成 `3E7B9C41-…` 且不再做
160 MiB 复制后，卷发布成功。此前那条 `publish failed Already started` 的日志
来自 `c75b22e` 之前的镜像。

## 2. 内存日志：本次没取到

`fastboot oem debuglog` 之后 `fastboot get_staged` 取回 **0 字节**。
原因不是发布失败，而是 UniXNU 接管控制台后固件不再泵 fastboot 端点：同一次会话里
紧接着的 `getvar product` / `getvar serialno` 全部 `AdbWriteEndpointSync failed`。
所以这一版没有 `DEBUG()` 记录，只有主机侧的 `OKAY` 与菜单表现。

下一版若要留下状态码，必须在 `oem ramdisk` 之后立刻取日志（窗口只有毫秒级），
或者把日志改到 UniXNU 自己的输出里。

## 3. 菜单与输入

- 条目：`xnu`（Xiaomi Pad 8 Pro: XNU first boot）、`Restart`、`Power off`
- 音量上/下移动高亮、电源确认，与 `42968500580` 的结论一致
- payload 卷内容在刷机前离线校验过：FAT32，512 B/扇区、4 扇区/簇、327680 扇区，
  `/EFI/UniXNU/unixnu.toml` 500 B，`Payloads/kernel.macho` 125,501,440 B +
  `kernel.adt` 12,112 B

## 4. 复现命令

```
fastboot boot boot-<build>.img
# 等 getvar product 返回 piano-uefi（约 9 s），再留 8 s 走完 0.5+2+2+3 s 的追踪暂停
fastboot stage payload-<build>.img
fastboot oem ramdisk
fastboot oem debuglog        # 只在固件仍泵端点时有效
fastboot get_staged uefi.log
```
