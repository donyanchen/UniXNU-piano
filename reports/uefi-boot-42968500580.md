# piano 启动记录 — 构建 `42968500580`（`f37b9f3`）

真机实测，2026-11-11。这一版包含 fastboot 等待期间手动泵 `FbPoll` 的修复、
`VolumeRead` 尾部短读修复，以及 ShengUfs 的 SM8750 GCC 时钟偏移。

## 1. 主机侧：payload 送进去了，但发布失败

```
$ fastboot boot boot-42968500580.img
Sending 'boot.img' (3088 KB)                       OKAY [  0.008s]
Booting                                            OKAY [  0.248s]

$ fastboot stage payload-42968500580.img
< waiting for any device >                          ← UEFI 的 fastboot 枚举上来
Sending '...payload-42968500580.img' (163840 KB)   OKAY [  1.370s]

$ fastboot oem ramdisk
FAILED (remote: 'cannot publish the payload')
```

`stage` 用 1.370 s 送完 160 MiB，说明 `PianoFastbootWaitPayload` 里手动泵
`FbPoll` 之前，那个 20 秒窗口里 USB 端点根本没人读的问题已经解决。

`oem ramdisk` 失败两次，结果一致，属确定性失败。当时的 `PublishVolume` 用
`AllocatePool (mDataSize)` 复制 160 MiB 缓冲，返回 out of resources，所以
`InstallMultipleProtocolInterfaces` 从未执行。已改为直接引用 stage 的传输缓冲
（提交 `c75b22e`），尚未复测。

## 2. UEFI 侧：内存日志

`fastboot oem debuglog` 之后 `fastboot get_staged` 取回 174006 字节。
注意 `Print ()` 只走 ConOut，不进这份日志；只有 `DEBUG ()` 经
`MemorySerialPortLib` 才落盘。

关键片段：

```

UNIXNU: UniXNU 0.1.0 starting as application, firmware Project Silicium rev 0x10000
UNIXNU: config: no boot entry found

UNIXNU: ui: graphics 1600x1068, scale 1, landscape layout

```

- `964E5B22-6459-11D2-8E39-00A0C969723B`（`EFI_SIMPLE_FILE_SYSTEM_PROTOCOL`）
  出现 7 次，即固件里有多个可读卷，但都不含 `\EFI\UniXNU\unixnu.toml`
- `input yes` —— UniXNU 认为存在输入设备，与实测按键可用一致
- `default 0 'exit'` 是内置配置的第一项，也就是 "Return to firmware"

## 3. 菜单按键：已验证

`patches/unixnu-menu-volume-keys.patch`（提交 `df23b53`）在真机上生效：

| 按键 | 效果 |
| --- | --- |
| 音量上 | 上移 |
| 音量下 | 下移 |
| 电源 | 确认 |

piano 的 `KeypadDeviceLib` 发 `SCAN_LEFT` / `SCAN_RIGHT` / `Enter`，而 UniXNU
的 `Menu.c` 只认 `SCAN_UP` / `SCAN_DOWN`，并且把 `SCAN_RIGHT` 当作"启动选中项"，
所以修补前音量键只能启动、不能移动高亮。

## 4. 复现命令

```
fastboot boot boot-<build>.img
# UEFI 先走完 0.5 + 2 + 2 + 3 s 的追踪暂停，然后才进入等待窗口
fastboot stage payload-<build>.img
fastboot oem ramdisk

fastboot oem debuglog
fastboot get_staged uefi.log
```
